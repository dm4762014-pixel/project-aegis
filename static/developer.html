Prove it in a controlled failure lab

Run real Chromium against five deliberately broken applications and a healthy control. Each is rerun against a preconfigured corrected version. This is a local experiment—not a production incident or an automatic repair.

Ready. Node.js, Playwright and Chromium are needed for the live lab.

Investigate a capture from your own app

In browser DevTools → Network, capture the failing page/action and export a filtered HAR. Import it here with the frontend and intended JSON API URL. No requests are made to those URLs.

HAR files can contain secrets. The raw file is sent only to this local server, held in memory, and not saved. Exports omit cookies, request headers, bodies, URL credentials, query strings and fragments; paths can still be sensitive. Maximum payload 1 MiB, 200 entries. HAR alone usually cannot confirm CORS or capture JavaScript exceptions.

What this version can and cannot establish

Covered signals: API 5xx/404 responses, observed browser CORS rejection, a failed alternate route while the intended API works, HTML from an expected JSON API, uncaught JavaScript errors in the live lab, and browser network/certificate error signals in a HAR.

Diagnoses are explicit rules, not a complete root-cause engine. Real sites are supported through HAR analysis; unattended browser checks are restricted to owned local fixtures. There is no login automation, production access, repository modification, deployment, or arbitrary-site browser runner. A healthy capture covers only its observed page load/action.

The lab uses port 8012 temporarily and refuses to run if it is occupied. It never stops an unrelated service. Fixed variants are supplied by the experiment, not generated or applied by the diagnostic tool.

Developed with substantial Codex assistance. Real user usefulness and production-incident accuracy remain unverified.
